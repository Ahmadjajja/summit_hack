TripCheck build spec

You chat in ASI:One, so we build no UI. SubQ Snap turns your words into a structured request and saves it to MongoDB. On a signal, it reads everything back and picks the plan. Gemini 4 Argon independently verifies it. You approve. The locker room pays only when new money goes out, and Fetch.ai agents execute. Every step is timed and costed.

Research

What we found, and how it shapes the design

Chat UI · use theirs

Don't build a chat. Use ASI:One.

  • An agent that speaks the Agent Chat Protocol gets a "Chat with Agent" button on Agentverse, which opens an ASI:One chat session.
  • Set mailbox=True and the agent runs on a laptop with no public URL. Agentverse queues messages for it.
  • Message types (ChatMessage, ChatAcknowledgement) come ready-made from uagents_core.

Decision: one orchestrator uAgent with the chat protocol and a mailbox. No frontend.

Important · SubQ Snap

Snap is a decision model, not a text writer

  • POST api.subq.ai/v1/systemone takes a state (up to 384K tokens) and 1–16 questions.
  • Each answer is a yes/no probability, a choice (2–255 labelled options, with a probability for each and a confidence), or a score.
  • Output tokens are always 0, so you pay input only. It can't write JSON or a plan as text.
  • Text-generating models (subq-1.4-small, subq-preview) need your organization to be enabled.

Decision: intake = Snap answers fixed questions about your message. Planner = Snap picks one option per trip slot from the candidates in MongoDB. Our code assembles the plan JSON from those picks.

Verifier · Gemini 4 Argon

The "Argon" model exists. Use it.

  • A reasoning model, reported around $2 / $10 per 1M input/output tokens at introductory pricing until Nov 30. Confirm in AI Studio.
  • Responses include usage_metadata (prompt and output token counts), so we can compute cost per call.
  • Gemini can also transcribe audio if we add voice later.

Decision: the verifier is Gemini 4 Argon with a JSON output schema. Hard math is done in Python checks.

Locker room · Fetch payments

Fetch already has a payment protocol

  • The Agent Payment Protocol lets a seller agent request payment and a buyer agent commit it. The official example uses Stripe sandbox, so no real money moves.
  • That is our locker room: an agent holding the Stripe test key that commits payment only after your approval and only up to the capped amount.

Decision: build the locker room as a payment agent, so the card never enters any prompt.

Voice

Voice: keep it out of the critical path

ASI:One chat is text. Gemini voice-to-text means building our own mic page, which brings back the UI we just removed. For the demo, type, or use your phone's or laptop's built-in dictation in the ASI:One box. Add a Gemini voice page only if there's spare time.

Caveat

Verify these three things in the first 15 minutes

  • Run GET /v1/models on SubQ and confirm the exact Snap model ID (the docs say both subq-snap-1.1 and subq-snap-preview).
  • Confirm your Gemini key can call Argon. If not, use the best Gemini Pro model you have.
  • Open "Chat with Agent" on a hello-world mailbox agent.

Final architecture

MongoDB in the middle, signals between steps

Steps never hand data directly to each other. Each step reads what it needs from MongoDB, does its work, then writes its result and its time and cost back. Only then does it send a small signal (trip ID + plan version) to the next step. Every plan version, every verdict and every cost is saved.

⚡ Signal (trip ID + version only) Read / write MongoDB Verifier rejects (max 3 loops) No new money New money: locker room first

run_log entry

Every step writes one of these. The scoreboard is a sum over them.

Sending a signal: the simplest version is the orchestrator calling the next step with {trip_id, version} right after the write succeeds. An option for later is for each step to watch MongoDB change streams on a status field.

Selling point

The scoreboard sent to chat

Every iteration logs time and cost per model, so you can show judges what verification costs against what it saves. The numbers below are a mock-up of the format. Real values come from the run log.

IterationSubQ timeSubQ costGemini timeGemini costVerdictTrip total

Cost formula. SubQ: input_tokens × the price per million (output is free). Gemini: in_tokens × input price + out_tokens × output price, read from usage_metadata. Put the prices in one config file and confirm them on each console.

Cancel, reschedule, extend: same loop

Extend"2 more nights in Osaka"Same hotel or alternative. New return flight.Return flight matches the new end date, nights continuous, within budgetvault · extension only

Reschedule order: book the new option first, then cancel the old one, so you're never left without a room.

Ask at the sponsor booths

Three questions worth two minutes each

SubQ booth

"Can you enable subq-1.4-small for our org?" If they do, intake can produce full JSON from your raw text, which matches what their team described to you. If not, the Snap-only design above still works.

Fetch booth

"Is the payment protocol plus Stripe sandbox the right way to do an approval-gated payment?" It's also worth asking if ASI:One accepts voice input.

Google booth

"Does our hackathon key have Gemini 4 Argon access, and what's the current price?" Put the answer in the cost config.
